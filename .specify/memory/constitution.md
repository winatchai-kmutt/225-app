# a255_app Constitution

## Core Principles

### Principle 1: Spec-Driven Development (SDD)

All development MUST follow the specifications generated by `/specify` and `/plan` commands. The plan is the single source of truth for implementation. No code changes shall be made without a corresponding specification document that has been reviewed and approved.

**Rationale**: Ensures all stakeholders have visibility into planned changes, reduces rework from misunderstood requirements, and creates a documented audit trail of architectural decisions.

### Principle 2: Separation of Rules (CRITICAL)

The project is governed by THREE separate rule files located in `.specify/memory/`:

- `constitution.md` (This file): Defines high-level meta-principles governing the development process, versioning, and governance procedures.
- `1_appendix.md`: Defines the non-negotiable Flutter Clean Architecture and folder structure that MUST be followed for all code organization.
- `2_theme.md`: Defines the non-negotiable Neo-Brutalist Fintech UI theme and widget design that MUST be followed for all user interface elements.

**Rationale**: Separating concerns allows each rule file to evolve independently. Architecture rules can be updated without changing governance procedures. Theme updates don't require constitution amendments. This modular approach prevents cascading changes across the project's rule system.

### Principle 3: Strict Architecture Compliance

All code MUST strictly adhere to the Flutter Clean Architecture rules and folder structure defined in `.specify/memory/1_appendix.md`. This includes:

- Following the prescribed folder hierarchy under `lib/`
- Implementing features using the presentation-domain-data layer separation
- Placing routing configuration in the designated location
- Adhering to Cubit/State file separation requirements
- Following dependency injection and service location patterns

**Rationale**: Consistent architecture enables predictable code organization, facilitates automated tooling and agent assistance, reduces onboarding time for new developers, and ensures maintainability at scale.

### Principle 4: Strict Theme Compliance

All user interface code MUST strictly adhere to the Neo-Brutalist Fintech design rules defined in `.specify/memory/2_theme.md`. This includes:

- Using the defined color tokens from the semantic color system
- Applying the specified typography roles and font families
- Implementing thick borders and hard shadows per the design style
- Following component design patterns for buttons, cards, and other UI elements
- Maintaining visual consistency across all screens and features

**Rationale**: A consistent design system creates a cohesive user experience, establishes brand identity, accelerates UI development through reusable patterns, and ensures accessibility standards are met uniformly.

### Principle 5: Quality Gates

All code MUST pass `flutter analyze` with zero errors before being committed or merged. Additionally, all code MUST meet the Quality Gates defined in `.specify/memory/1_appendix.md`, which include:

- Static analysis compliance
- Test coverage requirements (if specified)
- Code organization standards
- Documentation requirements
- Performance benchmarks (if applicable)

**Rationale**: Automated quality gates catch issues early, prevent technical debt accumulation, maintain code health, and reduce time spent in code review on mechanical issues.

## Development Workflow

### Specification-First Process

1. All new features begin with a specification document generated via `/specify` command
2. Specifications MUST be reviewed and approved before implementation begins
3. Implementation plans are created via `/plan` command, which reads all three rule files
4. Tasks are generated via `/tasks` command based on approved specifications
5. Code is written to fulfill tasks while maintaining compliance with all rules

### Code Review Requirements

- All pull requests MUST reference the originating specification document
- Reviewers MUST verify compliance with architecture rules (1_appendix.md)
- Reviewers MUST verify compliance with theme rules (2_theme.md)
- Reviewers MUST verify all quality gates pass
- No exceptions to core principles are permitted without a formal constitution amendment

## Governance

### Amendment Procedure

1. Proposed amendments MUST be documented with clear rationale
2. Version number MUST be incremented according to semantic versioning:
   - **MAJOR**: Backward incompatible changes to principles or governance
   - **MINOR**: New principles added or materially expanded guidance
   - **PATCH**: Clarifications, wording improvements, non-semantic refinements
3. Amendment date MUST be recorded in the Last Amended field
4. All affected templates and documentation MUST be updated to maintain consistency

### Rule File Compliance

All `/plan` commands MUST read and adhere to all three rule files:
- `constitution.md` (meta-principles and governance)
- `1_appendix.md` (architecture and folder structure)
- `2_theme.md` (UI theme and design system)

This constitution supersedes all other development practices. When conflicts arise between this constitution and other documentation, the constitution takes precedence. For technical implementation details, defer to the specialized rule files (1_appendix.md and 2_theme.md).

### Enforcement

- Automated CI/CD checks MUST enforce quality gates
- Code that violates architecture or theme rules MUST be rejected
- Complexity that violates principles MUST be justified in writing before proceeding
- Regular compliance audits should be conducted to ensure ongoing adherence
